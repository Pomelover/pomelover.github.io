1.1 OpenGL

学习笔记系列，教程：Joey de Vries《LearnOpenGL》，中文版地址 learnopengl-cn.github.io。

　　在开始这段旅程之前，需要先弄清楚 OpenGL 到底是什么。

　　通常它被认为是一个 API（Application Programming Interface，应用程序编程接口），其中包含一系列可以操作图形、图像的函数。但这个说法并不准确：

OpenGL 本身并不是一个 API，它仅仅是一个由 Khronos 组织制定并维护的规范（Specification）。

　　规范严格规定了每个函数该如何执行，以及它们的输出值；至于内部具体每个函数是如何实现（Implement）的，则由 OpenGL 库的开发者自行决定（译注：这里的「开发者」指的是编写 OpenGL 库的人）。

　　正因如此，具体的 OpenGL 库可以使用不同的实现，只要其功能和结果与规范相匹配即可——也就是说，作为用户不会感受到功能上的差异。

　　实际的 OpenGL 库的开发者通常就是显卡生产商：所购买的显卡支持哪个 OpenGL 版本，取决于针对该系列显卡专门开发的库。在 Apple 系统上，OpenGL 库由 Apple 自身维护；在 Linux 下，则既有显卡生产商提供的版本，也有一些爱好者改编的版本。

　　这也意味着，任何时候 OpenGL 库表现出的行为与规范不一致时，基本都是库的开发者留下的 bug。

Tip：这与 DirectX 形成对照——DirectX 由微软一家制定并主导，规范与实现的边界更集中；而 OpenGL 的规范由 Khronos 联盟制定、实现分散在各家驱动里，因此「同一段代码在不同驱动上行为略有出入」在 OpenGL 生态中更常见。游戏引擎往往同时维护 OpenGL / DirectX / Vulkan 多个图形后端，原因之一就在这里。

1.1.1 核心模式与立即渲染模式

　　早期的 OpenGL 使用立即渲染模式（Immediate mode），也就是通常所说的固定渲染管线。这个模式下绘制图形很方便，但 OpenGL 的大多数功能都被库隐藏了起来，开发者很少有控制 OpenGL 如何进行计算的自由。

　　开发者迫切希望能有更多的灵活性。随着时间推移，规范越来越灵活，开发者对绘图细节也有了更多的掌控。

　　立即渲染模式确实容易使用和理解，但效率太低。因此从 OpenGL 3.2 开始，规范文档开始废弃立即渲染模式，并鼓励开发者在核心模式（Core-profile）下进行开发——这个分支的规范完全移除了旧的特性。

　　在核心模式下，OpenGL 强制要求使用现代函数。一旦调用了某个已废弃的函数，OpenGL 就会抛出错误并终止绘图。

　　现代函数的优势是更高的灵活性和效率，代价则是更难学习。立即渲染模式从 OpenGL 的实际运作中抽象掉了大量细节，因此它容易学习，却很难让人把握 OpenGL 究竟是如何运作的。

　　现代函数要求使用者真正理解 OpenGL 和图形编程，它有一定难度，但提供了更高的灵活性、更高的效率——更重要的是，能够更深入地理解图形编程。

Tip：这条路线的下一站是 Vulkan——它不止移除旧特性，而是连 OpenGL 那套全局状态机也一并取消：对象由应用显式创建和持有，绘制命令先录制进命令缓冲，显存分配与 CPU/GPU 同步也全部交给应用自己管理。核心模式虽然迫使开发者使用现代函数，却仍然保留了「先绑定、再操作」的全局状态模型；Vulkan 则要求把每一步都写清楚。灵活性与使用成本同步上升，这个趋势其实在本节就已经埋下了。

1.1.2 扩展

　　OpenGL 的一大特性就是对扩展（Extension）的支持。当某个显卡公司提出一项新特性或者一项渲染上的重大优化时，通常会以扩展的形式在驱动中先行实现。

　　只要程序运行在支持该扩展的显卡上，开发者就可以使用它提供的更先进、更高效的图形功能。通过这种方式，开发者不必等待新的 OpenGL 规范面世，就能使用新的渲染特性——只需要简单地检查一下显卡是否支持该扩展即可。

　　通常，当一个扩展非常流行或者非常有用时，它最终会成为未来 OpenGL 规范的一部分。

1.1.3 状态机

　　OpenGL 自身就是一个巨大的状态机（State Machine）：一系列变量描述了 OpenGL 此刻应当如何运行。这些状态通常被称为 OpenGL 的上下文（Context）。

　　更改状态的途径通常是设置选项与操作缓冲；完成这些设置之后，便用当前的 OpenGL 上下文来渲染。

　　使用 OpenGL 时，会遇到两类函数：状态设置函数（State-changing Function）会改变上下文，状态使用函数（State-using Function）则根据当前 OpenGL 的状态执行相应操作。只要记住 OpenGL 本质上是个大状态机，就能更容易理解它的大部分特性。

Tip：全局状态带来一个长期麻烦：绘制调用之间会互相影响。某处忘了把状态改回去，出错的位置可能离真正的原因很远——这类 bug 极难定位，因为「现场」和「凶手」被隔开了。工程上的对策不是小心翼翼，而是不依赖残留状态：绘制每个物体之前显式设置它需要的全部状态，再按状态给绘制排序以减少切换开销。游戏引擎渲染器中的「状态排序」与「批处理」，动机正在于此。

1.1.4 对象

　　OpenGL 库是用 C 语言编写的，同时也支持从它派生出的多种语言，但其内核仍然是一个 C 库。由于 C 的一些语言结构不易被翻译到其他高级语言，OpenGL 在开发时引入了一些抽象层，对象（Object）就是其中之一。

小结

　　OpenGL 并不是一个 API，而是由 Khronos 制定并维护的规范；理解规范与实现的分工，是理解后续所有特性的前提。

  • 规范与实现分离：规范只约束函数的行为与输出值，实现细节由各家自行决定。实际的实现来自显卡厂商的驱动、Apple 自维护的版本，以及 Linux 上各类改编版本；行为与规范不符时，基本都是实现者留下的 bug。
  • 核心模式与立即渲染模式：立即渲染模式（固定管线）易学易用，但功能被库隐藏、可控性差、效率低；OpenGL 3.2 起被废弃，核心模式完全移除旧特性并强制使用现代函数，门槛更高，灵活性与效率也更高。
  • 扩展：厂商的新特性与重大优化以扩展形式先落在驱动中，无须等待新规范即可使用，只需检查显卡是否支持；足够流行或有用之后，扩展会被并入规范。
  • 状态机：OpenGL 是一个巨大的状态机，一系列变量描述了它此刻应当如何运行，这些状态即上下文；函数分为改变上下文的状态设置函数与依据当前状态执行操作的状态使用函数。
  • 对象：对象是状态的一个子集，用 id 引用，可以看作 C 风格的结构体；使用套路是创建 → 绑定至上下文的目标位置 → 设置选项 → 解绑，选项保存在对象中，重新绑定即重新生效。
