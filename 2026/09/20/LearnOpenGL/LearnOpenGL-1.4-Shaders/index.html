1.4 着色器

学习笔记系列，教程：Joey de Vries《LearnOpenGL》，中文版地址 learnopengl-cn.github.io。

　　着色器（Shader）是运行在 GPU 上的小程序，它们各自为图形渲染管线的某个特定部分而运行。从基本意义上说，着色器只是一种把输入转化为输出的程序。

　　着色器同时也是非常独立的程序，因为它们之间不能相互通信——彼此之间唯一的沟通只有通过输入和输出。

Tip：这里的「独立」有两层含义。一是阶段之间：顶点着色器的结果只能通过声明的 out 交给后续阶段，任何两个阶段的着色器都无法直接读写对方的变量（1.3 中链接出错，正是因为这条唯一的通路没对上名字与类型）。二是同一阶段内部：一个阶段里成千上万个着色器实例由 GPU 并行执行同一份代码，彼此不能共享局部变量，也不能互相等待或累加——需要在多个顶点、片段之间汇总数据时，只能由 CPU 侧的 uniform、纹理，或者变换反馈（Transform Feedback）、原子操作一类显式机制来完成。

1.4.1 GLSL

　　着色器是使用一种叫做 GLSL 的类 C 语言写成的。GLSL 是为图形计算量身定制的，它包含一些针对向量和矩阵操作的有用特性。

Tip：这些特性的直接体现是内置类型与函数：vec2/vec3/vec4、mat2～mat4 等类型，逐分量的算术与 swizzle（如 pos.xyz、color.rgb），矩阵乘向量写起来就是 mat4 * vec4，以及 dot、cross、normalize、reflect、mix 这类内置函数——它们大多直接映射到 GPU 的一条指令甚至硬件单元。反过来，GLSL 也没有指针、递归、动态内存分配，且必须给出确定的循环边界，因为同一份代码要在成千上万个实例上并行执行。写惯 C++ 后可以把它理解成「只留下数值计算的那部分 C，再补上一整套向量/矩阵语法」。

　　着色器的开头总是要声明版本，接着是输入和输出变量、uniform 和 main 函数。每个着色器的入口点都是 main 函数，在这个函数中所有的输入变量被处理，结果被输出到输出变量中。

1.4.2 数据类型

　　和其他编程语言一样，GLSL 也有数据类型，用来指定变量的种类。GLSL 中包含 C 等其它语言大部分的默认基础数据类型：int、float、double、uint 和 bool。GLSL 也有两种容器类型，它们在后文中会使用很多，分别是向量（Vector）和矩阵（Matrix）。

Tip：这些基础类型与 C++ 的名称相同，脾气却不大一样。GLSL 基本不做隐式类型转换——整数与浮点混算会直接编译失败，必须显式写出构造函数，如 float(i)、int(f)、vec3(1.0f, 0.5f, 0.2f)；bool 也只有 true/false 两个字面量，没有 C 的「非 0 即真」。另外 uint 是 GLSL 1.30 之后才加入的类型，在需要按位运算或作为整型顶点属性上传时才会用到。

向量

　　GLSL 中的向量是一个可以包含有 2、3 或者 4 个分量的容器，分量的类型可以是前面默认基础类型中的任意一个。它们可以是下面的形式（n 代表分量的数量）：

类型 含义
vecn 包含 n 个 float 分量的默认向量
bvecn 包含 n 个 bool 分量的向量
ivecn 包含 n 个 int 分量的向量
uvecn 包含 n 个 unsigned int 分量的向量
dvecn 包含 n 个 double 分量的向量

　　大多数时候使用 vecn，因为 float 足够满足大多数要求了。

Tip：分量个数与类型都写在类型名里，因此向量是一族固定长度的类型而非模板：分量数决定后缀，类型由前缀区分，写成 bvec4 就是「4 个布尔分量」。这种「长度固定」是它与 std::vector 的根本区别——它更像一个小的定长数组，长度在编译期就确定，没有动态增长这回事。另外在 std140 这类显存布局规则下，vec3 也会按 16 字节对齐，所以用一个 vec4 顶替 vec3 通常并不浪费空间。

　　一个向量的分量可以通过 vec.x 这种方式获取，这里 x 是指这个向量的第一个分量。分别使用 .x、.y、.z 和 .w 可以获取它们的第 1、2、3、4 个分量。GLSL 也允许对颜色使用 rgba，或是对纹理坐标使用 stpq，来访问相同的分量。

Tip：三套名字访问的是同一份数据，选哪一套不影响结果，只影响可读性。惯用法是按语义挑组：位置与方向用 xyzw，颜色用 rgba，纹理坐标用 stpq——在计算颜色的代码里写 color.rgb 比 color.xyz 更不容易让人误解。混着用虽然语法合法，但在团队代码里通常会被视为笔误的信号。

1.4.3 输入与输出

　　虽然着色器是各自独立的小程序，但它们都是一个整体的一部分。出于这样的原因，每个着色器都需要有输入和输出，这样才能进行数据交流和传递。GLSL 定义了 in 和 out 两个关键字专门来实现这个目的：每个着色器使用这两个关键字设定输入和输出，只要一个输出变量与下一个着色器阶段的输入匹配，它就会传递下去。但在顶点和片段着色器中会有点不同。

Tip：这条「输出接输入」的链路是按变量名（或显式声明的 layout (location = ...)）配对的——顶点着色器的 out 与片段着色器的 in 必须同名同类型才会被接上，1.3 里提到的链接错误正来自这里。另外 in 的取值来源随阶段而异：顶点着色器的 in 由 CPU 端通过顶点属性提供，片段着色器的 in 则是光栅化对顶点输出做插值后的结果——同一个关键字，在两端拿到的数据来源并不一样。

　　顶点着色器应该接收的是一种特殊形式的输入，否则就会效率低下：它的输入特殊在直接来自顶点数据。为了定义顶点数据该如何管理，使用 location 这一元数据指定输入变量，如此才能在 CPU 上配置顶点属性。

Tip：location 就是 1.3 中 layout (location = 0) 里那个 0——它把 GLSL 侧的 in 变量、glVertexAttribPointer 的第一个参数与 glEnableVertexAttribArray 的参数串成一条线。也可以省略 layout，让 OpenGL 自动分配位置，再用 glGetAttribLocation 反查；但位置一旦由驱动决定，就得靠查询结果去配置属性，多一层运行时依赖，因此显式写出 location 是更稳妥的做法。

　　另一个例外是片段着色器，它需要一个 vec4 颜色输出变量，因为片段着色器需要生成一个最终输出的颜色。如果在片段着色器中没有定义输出颜色，OpenGL 会把物体渲染为黑色（或白色）。

Tip：这正是 1.3 中片段着色器必须写出 out vec4 FragColor; 的原因，本节只是把那条要求讲清楚。输出的位置默认为 0，也可以显式写成 layout (location = 0) out vec4 FragColor;；等到使用多渲染目标（MRT）时，输出会有多个，各自的位置便与 glDrawBuffers 指定的附件一一对应。本节的程序只有一个颜色附件，因此只声明一个输出即可。

　　因此，若打算从一个着色器向另一个着色器发送数据，就必须在发送方着色器中声明一个输出，在接收方着色器中声明一个类似的输入。当类型和名字都一样的时候，OpenGL 就会把两个变量链接到一起，它们之间就能发送数据了——这是在链接程序对象时完成的。

Tip：类型要「一样」必须精确到分量数与类型本身，vec3 与 vec4 之间不会自动转换，这一点与前面「GLSL 不做隐式类型转换」的规则一致。另外要注意，着色器里声明了却没有真正被使用的变量，驱动的优化器可能直接把它删掉——此时用 glGetAttribLocation、glGetUniformLocation 去查会得到 -1，看上去像是「写错了名字」，实际只是该变量已被优化掉。

1.4.4 Uniform

　　uniform 是另一种在 CPU 上的应用程序向 GPU 上的着色器传递数据的方式，但它和顶点属性有些不同。首先，uniform 是全局的（Global）——全局意味着 uniform 变量必须在每个着色器程序对象中都是独一无二的，而且它可以被该着色器程序的任意着色器在任意阶段访问。其次，无论把 uniform 值设置成什么，uniform 都会一直保存它们的数据，直到它们被重置或更新。

Tip：这里的「唯一」是指在同一程序对象内部：顶点着色器与片段着色器可以各声明一个同名的 uniform，链接后它们其实是同一个变量，值也只有一份；不同的程序对象之间则互不影响，各自保存自己的副本。正因为这份数据属于程序对象而非某个着色器对象，glUniform* 系列函数只会作用于当前 glUseProgram 激活的那个程序——在 glUseProgram 之前设置 uniform 不会报错，但设置结果会落到别的程序（或什么都不落）上，是初学时很常见的一个坑。

　　要在 GLSL 中声明 uniform，只需在着色器中使用 uniform 关键字，并带上类型和名称。

　　如果声明了一个 uniform 却在 GLSL 代码中没有用过它，编译器会静默地移除这个变量，导致最后编译出的版本中并不会包含它，这可能引出几个非常麻烦的错误，这一点需要记住。

Tip：这类移除发生在链接阶段，而且不会有任何警告，因此「声明了却查不到位置」往往不是名字拼写的问题，而是该变量真的已经被优化掉：glGetUniformLocation 会返回 -1，随后所有针对它的 glUniform* 调用都会被忽略（-1 不是合法的位置值）。调试时若临时注释掉了使用某个 uniform 的代码，就要预期它随之消失，不要对着 -1 反复检查拼写。

i 函数需要一个 int 作为它的值
ui 函数需要一个 unsigned int 作为它的值
3f 函数需要 3 个 float 作为它的值
fv 函数需要一个 float 向量／数组作为它的值

Tip：位置值只是某个程序对象内部的索引，并不是显存的真实地址。它只在程序对象保持链接结果期间有效——一旦重新链接（或重新创建）程序，旧的位置值就作废了，所以把位置值缓存到程序重载之后使用是另一个容易被忽略的坑。

　　glVertexAttribPointer 函数的前几个参数比较明了：这次配置的是属性位置值为 1 的顶点属性，颜色值有 3 个 float 那么大，并且不打算标准化这些值。

　　由于现在有了两个顶点属性，就不得不重新计算步长值。为获得数据队列中下一个属性值（比如位置向量的下个 x 分量），必须向右移动 6 个 float，其中 3 个是位置值，另外 3 个是颜色值。这使步长值为 6 乘以 float 的字节数（= 24 字节）。同样，这次必须指定一个偏移量：对于每个顶点来说，位置顶点属性在前，所以它的偏移量是 0；颜色属性紧随位置数据之后，所以偏移量就是 3 * sizeof(float)，用字节来计算就是 12 字节。

Tip：最后一个参数虽然写着 void*，实际接收的是字节偏移量，所以颜色的偏移要做一次整数到指针的强制转换；当结构体字段变多时，用 offsetof(Vertex, color) 代替手写的 3 * sizeof(float) 更不容易算错（需要 #include <cstddef>）。另外别漏掉每个属性后面的 glEnableVertexAttribArray——顶点属性默认禁用，只配置指针而不启用，GPU 依旧读不到这个属性。

小结

　　本节从着色器本身讲起，依次补齐了它的书写语言、数据类型、阶段之间的输入输出、由 CPU 传入的 uniform 与顶点属性，最后把整套编译链接流程封装成一个类。

  • 着色器与 GLSL：着色器是运行在 GPU 上、为渲染管线某一阶段服务的小程序，本质上是把输入转化为输出的程序，彼此之间只能靠输入输出通信；它用类 C 的 GLSL 编写，天然带有向量与矩阵运算特性。顶点着色器中每个输入变量也叫顶点属性，其数量上限由硬件决定，可用 GL_MAX_VERTEX_ATTRIBS 查询（至少 16 个 4 分量属性）。
  • 数据类型：基础类型为 int、float、double、uint、bool，容器类型是向量与矩阵。向量按「前缀表类型、后缀表分量数」命名（vecn、bvecn、ivecn、uvecn、dvecn），分量可用 xyzw、rgba、stpq 三套名字访问，并通过重组（Swizzling）任意挑选、重复分量来构造新向量。
  • 输入与输出：in 与 out 负责阶段之间的传值，输出与下一阶段的输入必须类型与名字都一致，链接程序对象时才会被接上；顶点着色器的输入来自顶点数据、用 location 指定位置值，片段着色器则必须声明一个 vec4 颜色输出。
  • uniform：由 CPU 侧设置，在程序对象内全局唯一，并且会一直保存数据直到被更新；glGetUniformLocation 负责查询位置值（返回 -1 表示没有找到），设置前必须先调用 glUseProgram，函数后缀标识参数类型，如 glUniform4f 对应 4 个 float。声明了却未使用的 uniform 会被编译器静默移除——本节例子用 sin(glfwGetTime()) 让它随时间改变颜色。
  • 更多属性：顶点数据追加 3 个 float 颜色分量后，位置与颜色要分别调用 glVertexAttribPointer；交错布局下两者的步长都是 6 个 float（24 字节），颜色属性的偏移为 3 * sizeof(float)（12 字节）。画面中的连续渐变来自光栅化的片段插值——它按片段在三角形中的相对位置，对所有片段着色器的输入变量做插值。
  • 着色器类：为免去反复编写、编译与错误检查的麻烦，本节末尾封装出一个 Shader 类，它从硬盘读取着色器源码并完成编译、链接与错误检测，使用时只需构造对象，再调用 use() 与 setFloat() 等接口。
