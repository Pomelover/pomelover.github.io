第 4 章 贵族专制、民主政治和系统设计

读书笔记系列，书籍：Frederick P. Brooks, Jr.《人月神话》（The Mythical Man-Month）。

　　本章由一段对兰斯大教堂的描述开篇：

大教堂是艺术史上无与伦比的成就。它的原则既不乏味也不混乱……真正达到了风格上的极致，完成这件作品的艺术家们，完全领会和吸收了以往的成功经验，也完全掌握了他们那个时代的技术，而且在应用的时候做到了恰如其分，绝不轻率，也绝不花哨。

Tip：这段文字出自兰斯大教堂的导览手册，是 Brooks 为全章设置的引子——教堂历代的建造者都尊重了最初的总平面设计，作品因此高度统一。它对应到软件上，正是本章的主题概念完整性（conceptual integrity）：设计若出自一个头脑、或少数意见一致的头脑，各部分的取舍才会彼此协调；而大多数欧洲大教堂恰恰相反，不同世代、不同建造者各自改进前人的方案，风格因而彼此抵触。

4.1 概念完整性

　　在绝大多数欧洲的大教堂中，由不同时代、不同建筑师所建造的各个部分之间，在设计或结构风格上都存在着许多差异。后来的建筑师总是试图在原有建筑师的基础上有所“提高”，以反映他们在设计风格和个人品味上的改变。

Tip：这种“提高”的动机往往是善意的——每一位后来者都在回应自己时代的审美与个人偏好，结果却是同一座建筑中并存着彼此抵触的风格。它正是本章用来对照软件的反面样本：局部的改进意愿累积起来，损害的是整体的统一。

　　与之对应的是，法国城市兰斯（Reims）在建筑风格上的一致性与上述大教堂形成了鲜明的对比。设计的一致性和那些独到之处一样，同样让人们赞叹和喜悦。

Tip：这句话值得留意——一致性本身也是一种可被欣赏的品质，而不是才华不足时的妥协；对系统而言，它同样不是“没有亮点”，而是让所有亮点指向同一个方向。

　　对于计算机系统而言，尽管它们通常没有花费几个世纪的时间来构建，但绝大多数系统体现出的概念差异和不一致性远远超过欧洲的大教堂。这通常并不是因为它由不同的设计师们相继开发，而是由于设计被分成了由若干人完成的若干任务。

Tip：对照第 2 章的沟通开销可以看清这一点：把设计切成若干份交给若干人，得到的并不是若干份并行的进度，而是若干套各自成立、彼此不协调的设计思路。这也与第 3 章末尾“由系统结构师从上至下进行所有的设计”前后相接——一体化设计正是为了避免这种分解带来的不一致。

　　由此引出的主张是：在系统设计中，概念完整性应该是最重要的考虑因素。也就是说，为了反映一系列连贯的设计思路，宁可省略一些不规则的特性和改进，也不提倡独立和无法整合的系统，哪怕它们其实包含着许多很好的设计。

Tip：这是一条取舍原则，而不是对功能的否定——功能的多少与概念复杂度之间的比值才是系统设计的最终检验标准，只有功能或只有简单都只实现了一半的目标。因此被省略掉的那些“很好的设计”，代价换来的是使用者不必记住互相冲突的惯例与例外。

　　本章和随后的两章将解释这个主题在编程系统设计中的重要性，需要回答的问题有：

  1. 如何得到概念的完整性？
  2. 这样的观点是否要有一位杰出的精英——或者说是结构设计师的贵族专制——以及一群创造性天分和构思被压制的平民编程实现人员？
  3. 如何避免结构设计师产出无法实现、或者是代价高昂的技术规格说明，而使大家陷入困境？
  4. 如何才能与实现人员就技术说明的琐碎细节充分沟通，以确保设计被正确地理解，并精确地整合到产品中？

4.2 获得概念的完整性

　　编程系统（软件）的目的是使计算机更加容易使用。为了做到这一点，计算机装备了语言和各种工具，这些工具实际上也是被调用的程序，受到编程语言的控制。使用这些工具是有代价的：软件外部描述的规模大小是计算机系统本身说明的十倍。用户会发现，寻找一个特定功能是很容易的，但相应却有太多的选择，要记住太多的选项和格式。

Tip：这里的“外部描述”指用户看到的接口说明——计算机的使用手册、编译器的语言手册、控制程序的语言手册等，而不是程序的实现说明。十倍这个量级解释了此后讨论的立足点：易用性并不由功能多少单独决定，而取决于功能规格说明省下的时间，是否超过学习、记忆与查阅手册所花掉的时间。

　　只有当功能说明节约下来的时间，超过用在学习、记忆和搜索手册上的时间时，易用性才会得到提高。由于目标是易用性，功能与理解上复杂程度的比值才是系统设计的最终测试标准。单是功能本身、或者单是易于使用，都无法成为一个好的设计评判标准。

Tip：把这个比值当作标准，意味着设计取舍不能只看两端——功能清单越长，使用者需要记住的例外、惯例与格式也可能同步增长；概念越精简，能表达的东西也可能随之减少。真正要守住的是二者之比，这也与 4.1 中“宁可省略一些不规则的特性和改进”是同一原则的量化表述。

　　这一点常被广泛地误解。OS/360 因复杂强大的功能而受其开发者推崇——功能而非简洁，一直被用来衡量设计人员的出色程度；PDP-10 的时分系统则因简洁与概念的精干而被建造者称道，尽管它的功能与 OS/360 并不在一个数量级上。而以易用性为衡量标准，单看功能与单看易用都是不均衡的，各自只达到了真正目标的一半。

　　对于给定级别的功能，能用最简洁和直接的方式来指明事情的系统是最好的。简洁和直白来自概念的完整性：每个部分必须反映相同的原理、原则和一致的折衷机制；在语法上，每个部分应使用相同的技巧，在语义上则应具有同样的相似性。因此，易用性实际上需要设计的一致性和概念上的完整性。

Tip：这里有“简洁”与“直白”两重意思，二者并不等价。概念数量少只做到了简洁——若表达意图需要基本设施的迂回组合，使用者除了元素与组合规则，还得记住一整套实际使用的习惯用法，这样的系统仍谈不上直白。两者同时成立，才说明设计出自同一套原理。

4.3 贵族专制统治和民主政治

　　概念的完整性要求设计必须由一个人，或者非常少数互有默契的人员来实现。

　　而进度压力却要求很多人员来开发系统。有两种方法可以解决这种矛盾：第一种是仔细地区分设计方法和具体实现；第二种则是前一章中所讨论的、一种崭新的组建编程开发团队的方法。

Tip：这两条出路分别承接此前的内容——前一种把体系结构与实现分开，正是第 3 章末尾由系统结构师从上至下设计的那条分工（下文会完整说明 architecture 与 implementation 的界线）；后一种即第 3 章的外科手术队伍。二者一个解决设计出自少数人，一个解决人力规模，合起来才回应了本节开头的矛盾。

　　对于非常大型的项目，将设计方法、体系结构方面的工作与具体实现相分离，是获得概念完整性的强有力方法。

　　体系结构（architecture）指的是完整和详细的用户接口说明：

  • 对于计算机，它是编程手册；
  • 对于编译器，它是语言手册；
  • 对于控制程序，它是调用其功能的语言和函数调用手册；
  • 对于整个系统，它是用户要完成自己全部工作所需参考的手册的集合。

Tip：这里的关键是把体系结构限定在“用户可见的接口”上，而不是内部的模块划分与数据结构。按今天的说法，公开头文件、语言规范、命令行与配置项的语义属于体系结构，而内部实现方式不属于。

　　因此，系统的结构师如同建筑的结构师一样，是用户的代理人。结构师的工作，是运用专业技术知识来支持用户的真正利益，而不是维护销售人员所鼓吹的利益。

　　体系结构同实现必须仔细地区分开来。如同 Blaauw 所说的：

体系结构陈述的是发生了什么，而实现描述的是如何实现。

Tip：这条界线划定了改动的边界：体系结构是使用者依赖的契约，其变动必须由结构师统一决定，而同一体系结构之下允许存在多种实现。今天的 C++ 里，头文件描述使用者依赖的约定、实现文件可自由替换，正是把这条区分落到了文件与语言机制上。

　　至于贵族专制统治的问题，答案必须既说“是”，也说“否”。就“是”的一面而言：结构师只能存在少数，他们的工作产物的生命周期比实现人员的产物更长，并且结构师一直处在解决用户问题、实现用户利益的核心地位。如果要得到系统概念上的完整性，那么必须控制这些概念。这实际上是一种无需任何歉意的贵族专制统治。

Tip：这里的“贵族专制”指的是概念的控制权集中，而不是人的高下之分——结构师的权威来自他对用户利益的代言责任，以及其产物需要长期被依赖这一点；正因为如此，第 3 章中“概念出自一人”的设定在此才被正面称作无需歉意的。

　　第二个问题的答案是否定的：外部技术说明的编制工作并不比具体的设计实现更富有创造性，它只是一项性质不同的创造工作而已。在给定体系结构下的设计实现，同样需要同编制技术说明一样的创造性、同样新的思路和卓越的才华。实际上，产品的成本性能比很大程度上依靠实现人员，就如同易用性很大程度上依赖结构师一样。

Tip：这里的“第二个问题”指 4.1 结尾所列四问中的第二问——设计是否要由一小群精英结构师主导，而使实现人员的天分与构思被压制。它与上一段同属一问的两面：上一段是“是”，承认少数人必须掌握概念；本段是“否”，说明实现人员并未因此失去创造的空间。

　　有很多行业和领域中的案例让人相信，纪律和规则对行业是有益的。正如某位艺术家的格言所说：“没有规矩，不成方圆。”最差的建筑往往是那些预算远远超过起始目标的项目。巴赫曾被要求每周创作一篇形式严格的康塔塔，但这似乎并没有压制他的创造性。

Tip：这条格言的含义是，约束并不与创造对立——形式被限定之后，精力便从“该做成什么”转向“如何做得更好”。两个例子都指向同一件事：预算充裕而目的不清的建筑反而最差，而每周期限与固定曲式的合唱作品照样能写出经典。放到软件上，这也说明预先给定的体系结构不会限制实现人员的发挥，反而免去了他们反复争论“接口该是什么”的开销。

　　类似地，外部的体系结构规定实际上是增强、而不是限制实现小组的创造性。一旦他们将注意力集中在没有人解决过的问题上，创意就开始奔涌而出。相反，在毫无限制的实现小组中，进行结构上的决策时会出现大量的想法和争议，对具体实现的关注反而会比较少。

　　这样的结果曾多次出现，R. W. Conway 也证实了这一点——他在 Cornell 的小组曾编制 PL/I 语言的编译器：

最后我们的编译器决定支持不经过改进和增强的语言，因为关于语言的争议已经耗费了我们所有的时间和精力。

Tip：这句话是上一段的反面证据：当“语言该是什么样”尚未定论时，争论会把小组的精力消耗干净，以致无人有余力做实现。Conway 小组的做法是接受一门既有的语言规格，把全部力量投入编译器的实现——这正是“外部体系结构增强而非限制创造性”的实例。

4.4 在等待时，实现人员应该做什么？

　　概念的完整性确实要求系统只反映唯一的设计理念，用户所见的技术说明来自少数人的思想。实际工作被划分成体系结构、设计实现和物理实现，但这并不意味着该开发模式下的系统需要更长的时间来创建。经验显示恰恰相反：整个系统将会开发得更快，所需要的测试时间将更少。同工作的水平分割相比，垂直划分从根本上大大减少了劳动量，结果是使交流彻底地简化，概念完整性得到大幅提高。

Tip：这里的垂直划分指按体系结构、设计实现、物理实现三个阶段分工，而不是把同一层工作横向切成若干块分给若干人——第 3 章的外科手术队伍、本节的架构与实现分离都是这一思路。它的收益不来自任何阶段的加速，而来自交流路径的减少：需要共同确认的事情变少，一体化设计因此得以保持。

小结

　　本章由兰斯大教堂的风格统一说起，主张概念完整性是系统设计中最重要的考虑因素，并说明它如何获得、代价是什么。

  • 概念完整性：欧洲大教堂各部风格彼此抵触，源于后来者各自“提高”前人的设计；计算机系统虽未历经数代，概念上的不一致却更为严重，原因通常不是设计师相继开发，而是设计被分给了若干人。因此宁可省略不规则的特性和改进，也要保持一系列连贯的设计思路。
  • 获得概念的完整性：软件的目的是让计算机更易使用，而外部描述的规模是计算机自身说明的十倍；只有当功能说明省下的时间超过学习、记忆与查阅手册的时间，易用性才提高。于是功能与理解上复杂程度的比值成为系统设计的最终检验标准，单看功能或单看简洁都只做到一半；简洁与直白来自概念完整性，要求各部分在原理、折衷机制、语法技巧与语义上都保持一致。
  • 贵族专制与民主政治：概念完整性要求设计出自一个人或少数互有默契的人，进度压力却要求大量人手；解法是把体系结构与实现分开，并采用第 3 章的外科手术队伍。体系结构即完整详细的用户接口说明，结构师是用户的代理人；Blaauw 指出体系结构陈述“发生了什么”，实现描述“如何实现”。贵族专制的答案是既“是”也“否”——是，概念必须由少数人控制；否，实现同样是第一等的创造性工作，产品的成本性能比主要取决于实现人员。
  • 纪律与创造：外部的体系结构规定增强而非限制实现小组的创造性，毫无限制的小组反而把精力耗在无止境的争论上；Conway 在 Cornell 编制 PL/I 编译器的经验正说明了这一点。
  • 落点：把工作按体系结构、设计实现、物理实现垂直划分，与水平分割相比大幅减少了交流量，系统开发得更快、测试时间更少，概念完整性也得到提高。
